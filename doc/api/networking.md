# 内容网络通信指南

适用：框架 6.0.0 / API 6 / 联机协议 19 / manifest 2。接口签名见 [PartyNet](reference.md)，生命周期见 [准备与关闭](api.md)。

## 首要原则

**仅传输必要数据，尽可能将不连续的数据一次性传输后交由本地处理。**

先回答“远端要知道哪个事实才能继续”，再选通信方式。一次动作、一次结果、一次阶段切换通常只需要一个小型可靠消息。动画曲线、字体、纹理、音效、每帧动画进度和可以由已知参数算出的中间值留在本地。

**禁止以周期性全量游戏/世界快照作为小游戏的默认通信方式。** 不允许把完整模型、整片地形、全部角色、历史记录和每帧计时一起广播，再用收到的状态覆盖本地画面。不能只把 snapshot 改名为 state 或 event 后继续发送相同内容，也不能用可靠队列积压已经过时的运动状态。

一次性场景初始化、规则锁定、离散事实变更、最终结果，以及少量必要的角色位置采样有明确用途，不属于上述禁止的持续全量快照。存档和 API 返回的只读数据副本也不是逐帧联网策略。连续运动同步只包含需要呈现的最少属性；能由事件与参数推导的内容不重复发送。

此规则约束新内容与现有正式入口。本次迁移范围和各玩法采用的组合见文末；未接入框架的独立原型不是联网范例。

## 框架负责什么

- ENet 直连；地址支持 IPv4、IPv6、域名及地址加端口格式。域名异步解析，连接/握手有超时，取消会关闭连接。
- 保留“客机必须安装房主全部协议、主游戏、小游戏，名称与版本匹配”的规则；不只检查选中池。允许客机额外内容，不计算文件哈希。
- 固定会话和作用域、必要端加载屏障、首次时钟同步、最终结果发布、作用域清理。
- 每秒读取 ENet 原生 RTT 与波动统计，提供通信活跃度与状态；大厅和游戏边角显示延迟，不为测速另发探测。
- 大厅掉线移除；局内标记退出并通知内容；房主离开结束会话。不提供重连或房主迁移。

框架不决定谁模拟物理、谁判分，也不自动提供预测、回滚、角色插值。不要新建或替换 MultiplayerPeer。小游戏根节点已经位于有效 MultiplayerAPI 下，可以直接写原生 @rpc。

## 常见功能与通信组合

频率是初始调参建议，不是保证体验的固定标准；由速度、人数和实际带宽决定。

| 功能 | 数据与通信方式 | 本地处理 |
|---|---|---|
| 回合/阶段切换 | 房主可靠发 phase_id、阶段参数、start/end_msec，一次 | 本地计算倒计时；到零等待房主明确切阶段 |
| 拍卖、出牌、棋步、选择 | 客机可靠发逻辑动作、回合号、action_id；房主验证后可靠公布变更 | 输入反馈立即显示，合法性和最终结果由指定裁判决定 |
| 结算与排名 | 一次可靠发 result_id、最终数值、必要分项、展示时序 | 数字滚动、逐项揭示、奖励飞行、音效全部本地播放 |
| 私人手牌/情报 | 仅可靠定向给所有者；只发新增或变更字段 | 本地卡片布局和揭示；不得把秘密先广播再隐藏 |
| 人物、可交互物件生成/销毁 | 优先 MultiplayerSpawner；生成参数含稳定 ID、所属 peer、出生点和资源 ID | 各端生成同一场景；装饰子节点由场景自带 |
| 持续角色操控 | 逻辑移动轴、瞄准方向、输入序号，20–30 Hz 不可靠有序；静止可降频 | 本地拥有者立即响应；房主模拟或作者明确采用所有者权威 |
| 跳跃、开火、换弹等边沿输入 | 小型可靠事件或带序号的明确确认机制；不要只发一帧不可靠 bool | 本地预播，重复 action_id 不产生第二次效果 |
| 远端人物姿态 | MultiplayerSynchronizer 仅同步目标位置/旋转/必要速度，15–30 Hz | 视觉子节点插值，常以 50–100 ms 缓冲起步；不直接反复覆盖本机控制角色 |
| 血量、弹药、得分 | 可靠变化事件，或 Synchronizer ON_CHANGE 小属性 | 飘字、闪烁与计分动画本地完成 |
| 炮弹 | 原生生成/销毁或可靠 spawn/despawn；需要修正时 15–30 Hz 不可靠运动采样 | 简单轨迹由初始位置/速度/开始时间推导；复杂碰撞由权威端判定 |
| 地形破坏 | 可靠发破坏事件或实际改变的格子/区段 | 不重复发送未改变地形 |
| 命中特效/爆炸 | 可靠发 event_id、位置、类型、必要强度；伤害结果单独明确 | 本地粒子、声音、震屏；不传粒子位置 |
| 环境风向/天气 | 参数变化时可靠发送；可一次发种子与时间表 | 本地生成不影响裁判的装饰 |
| 音游 | 一次可靠发谱面资源 ID、种子和开始时间；按规则上报成绩 | 本地音频时钟与判定；不能以网络包到达频率驱动节拍 |
| 光标/瞄准预览 | 15–30 Hz 不可靠有序，只发位置/方向；变化小则不发 | 本地平滑；丢一包等待下一包 |
| 语音 | 使用 api.voice | 不把 PCM 混入玩法可靠消息 |
| 退出与结果提交 | 订阅 player_disconnected；房主调用 finish | 排名规则由玩法定义；不在本地动画结束时重复发奖 |

## 直接使用原生 RPC

原生通道 0–7 可用；高频 RPC 推荐 1–7。0 同时承载 Godot 场景复制与框架可靠生命周期控制，避免在这里塞大载荷。8 为内容下载可靠通道；9 时钟；10 语音；11–22 为 PartyNet 内部用途，禁止直接占用。

下面是场景脚本中的接收入口。actor_peer 必须在所有端的生成阶段一致赋值；不要从载荷里相信自报身份。

```gdscript
var actor_peer: int
var last_input_sequence: int = -1
var move_axis: Vector2 = Vector2.ZERO
var last_input_msec: int = 0

@rpc("any_peer", "call_remote", "unreliable_ordered", 1)
func submit_move(sequence: int, axis: Vector2) -> void:
    if not api.is_host() or multiplayer.get_remote_sender_id() != actor_peer:
        return
    if sequence <= last_input_sequence or not axis.is_finite() or axis.length_squared() > 1.01:
        return
    last_input_sequence = sequence
    move_axis = axis
    last_input_msec = Time.get_ticks_msec()
```

客机调用 submit_move.rpc_id(1, sequence, axis)，检查返回 Error。房主的本机输入直接走同一内部动作处理函数；本地直接调用时 remote_sender_id 不代表远端，不能伪造发送者。持续输入按限频发送，松开时立即发中性值；丢包时后续样本继续重复当前值。权威端应在约 150–250 ms 没有新输入后将旧移动输入置零，避免最后一个松开包丢失导致持续行走。阈值按玩法调节，不用它决定会话掉线。

可靠事件使用 @rpc("any_peer", "call_remote", "reliable", 2)。房主公布事件可用 @rpc("authority", "call_local", "reliable", 2)，但节点 authority 必须确实属于房主；角色拥有者权威与框架房主身份是两个不同概念。

原生 RPC 要求两端对应节点路径和 RPC 声明一致。固定的活动实例根由框架提供，动态网络节点交给 Spawner；不要随机命名后期待 rpc_id 自动找到。原生 RPC 不经过 PartyNet 的 scope 过滤；party_stop 必须停止发送和计时器。不要跨不同通道假设“先发的一定先到”。依据 [Godot 高层联网说明](https://docs.godotengine.org/en/stable/tutorials/networking/high_level_multiplayer.html)。

## PartyNet：需要作用域路由时使用

不用 manifest streams/native_channels；可靠性写在调用处：

```gdscript
# 逻辑动作，默认可靠。
var error: Error = api.net.send_to_host(&"bid", {
    "round": round_id, "action_id": action_id, "amount": amount
})
if error != OK:
    api.fail("bid_send_failed", error_string(error))
    return

# 房主一次发布结算；默认包含本机，每端只收到一次。
error = api.net.broadcast(&"settlement", {
    "result_id": result_id, "scores": scores,
    "start_msec": api.net.host_time_msec(), "duration_msec": 4000
})
if error != OK:
    api.fail("settlement_send_failed", error_string(error))
    return

# 可被下一份取代的运动属性，逻辑通道 1。
error = api.net.send_to_host(&"move", input_data,
    MultiplayerPeer.TRANSFER_MODE_UNRELIABLE_ORDERED, 1)
```

send_to_group 允许任意成员发送到 instance / participants / spectators；broadcast 限房主。send_to_player / send_to_peer 支持相同可靠性选项。接收 message_received(sender, topic, payload)，只信 sender.peer_id / player_ids，不信 payload 自报的玩家。

PartyNet channel=0..3 是逻辑通道，并非上面的原生通道编号。每种可靠性单独映射；不同 topic 在同模式同通道仍共享队列，不获得独立优先级。大小差异明显的运动流使用不同逻辑通道，关键事件与运动分离。跨模式或跨通道若有依赖，带 phase_id、spawn_id 或 revision；先到的运动包可以有限暂存或丢弃等待下一份，不能据此创建未获授权的对象。

载荷支持 Godot 可序列化的基础值、向量、Packed 数组和嵌套数组/字典，不传 Node、Resource 或其他 Object。消息字典键可用 String、StringName 或整数实体 ID；持久化主游戏状态、配置和结果仍使用字符串键。游戏在网络入口验证身份、字段、范围与当前阶段。

只有必须观察远端处理完成时才增加业务 ack，例如场景就绪、结算页挂载。可靠传输已经重传丢包，不应再每帧重复发送同一结算。OK 不等于远端处理完成。避免把目标 1 当作永久玩家身份：它仅代表本次房主端点。

离散事件与运动样本分属不同通道时，运动样本带当前事件 revision 和递增 sample。先到的运动样本若依赖尚未到达的生成/回合事件，只保留最新一份等待；旧 revision 的运动不覆盖新阶段、重生或可靠停止位置。不要建立无限补包队列。

## 原生生成与属性同步

推荐场景：

```text
Game
├─ Actors
└─ MultiplayerSpawner (spawn_path = ../Actors)
   自定义 spawn_function 返回 Actor；不要在函数内自行 add_child

Actor
├─ Visual
└─ MultiplayerSynchronizer (root_path = ..)
```

生成前配置 spawn_function；房主在 party_start 后调用 spawn({id, peer_id, position})。各端函数用同一参数实例化角色，先设名字、初始位置、控制者字段和 authority，再返回尚未入树的节点。authority 的设置不会自行传播，必须由各端生成逻辑一致执行。退场时由生成权威释放节点；仅生成权威能生成和销毁。见 [MultiplayerSpawner](https://docs.godotengine.org/en/stable/classes/class_multiplayerspawner.html)。

建议保留 Actor/Spawner 的房主权威，将“哪个 peer 可提交此角色输入”保存在控制者字段；如需拥有者权威，只对明确的输入组件设为该 peer，别递归把整棵角色和伤害裁判都交出去。

Synchronizer 用 SceneReplicationConfig 列出最少属性；出生参数标记 spawn。持续目标位置使用 ALWAYS（不可靠），replication_interval 从 0.05 秒开始；低频小属性使用 ON_CHANGE（可靠）。不要同步整个 state 字典、动画播放器时间或 Node/Resource 引用。见 [MultiplayerSynchronizer](https://docs.godotengine.org/en/stable/classes/class_multiplayersynchronizer.html) 与 [SceneReplicationConfig](https://docs.godotengine.org/en/stable/classes/class_scenereplicationconfig.html)。

Synchronizer 负责传输属性，不自动提供适合玩法的网络插值。同步 target_position/target_rotation 等目标字段，Visual 在本地渲染帧插值；碰撞体留给裁判端。瞬移事件明确重置插值缓存。外推应有上限（如 100–150 ms），超限保持或显示等待，不能无限外推穿墙。丢包不调整 Engine.time_scale，也不把所有游戏计时器一起拉快/拉慢。

## 时间、结算和阶段

api.net.host_time_msec() 提供主机单调时钟估计；首次同步前返回 -1，准备屏障会等待首次同步。is_clock_ready() 表示样本是否新鲜；样本过期后显示时间仍前进。它不是音乐采样时钟，也不意味着客机可以裁决超时。

房主一次发送 end_msec，显示端每帧计算 max(0, end_msec - host_time_msec())。不要反复发送“还剩 12.3 秒”，更不要每次收包重新启动动画。阶段号只增不减，旧回合动作拒绝；归零后等待房主的下一阶段事件，禁止自行触发结算与下一局。

结算包含所需分项和时间安排，一次可靠发送；本地播完整动画。需要所有人看到结算再继续时，各端可靠确认“页面已挂载”，房主统一发布展示截止时间，最后明确发布继续事件。慢端直接恢复到当前展示进度，不重播已经完成的整轮；金额与排名不能在动画回调里再次写入权威账本。

## 延迟与掉线

大厅和游戏中按住 **Tab** 显示框架玩家/延迟面板，松开、失焦或进入设置/模态页时关闭。面板只读、不暂停游戏、不改变鼠标捕获；总积分入口改为 **F3**。房主行显示“房主”，不伪造链路 0 ms；没有首个样本显示“测量中”，过期显示“无响应”，断线显示“已掉线”。显示的是到房主的 RTT，不是任意两名客机之间的延迟。

延迟数据直接来自 `ENetPacketPeer.get_statistic(PEER_ROUND_TRIP_TIME)`，波动读取 `PEER_ROUND_TRIP_TIME_VARIANCE`。连接每秒读取一次原生统计并缓存，不发送测速请求，也不对 ENet 已计算的结果重复平滑；房主每秒向客机汇总其他玩家的统计。面板可见时每 0.5 秒读取缓存，大厅每秒只刷新玩家状态文字；打开/名单变化即时刷新，不追加网络请求，也不建立客机互相 ping 的网状通信。

Tab 面板额外显示一位小数的丢包率，直接读取 `PEER_PACKET_LOSS / PACKET_LOSS_SCALE × 100`。这是发送端可靠包丢失的平滑估计，ENet 在有发送数据时约每 10 秒更新，不是严格的最近 10 秒全量 UDP 丢包率。首个原生统计周期完成前显示“测量中”，房主自身、掉线及无响应行显示“—”。客机自己的行取客机→房主方向；其他玩家取房主→客机方向。数据随既有每秒链路汇总传输，不新增探测、确认或独立统计消息。

时钟校准仍由客机每秒向房主发起一次四时间戳请求，未返回的请求在 3 秒内不重发。它只用于估计房主时钟偏移，不再计算面板 RTT；原先房主向客机发起的测速探测已移除。原生 RTT 不包含远端时钟读数，不能替代校时。校时与统计汇总使用独立不可靠时钟通道。

这里的 1 秒是本项目面向 1–8 人显示与校时的取舍，不是统一行业标准。[Godot ENetPacketPeer 文档](https://docs.godotengine.org/en/stable/classes/class_enetpacketpeer.html)说明 ENet 自动维护可靠包的平均 RTT，默认空闲 ping 间隔为 500 ms。本次调整不额外调用 `ping()`，不改变该默认间隔，沿用框架已有的 `set_timeout(8, 5000, 15000)` 掉线配置。

连接 api.net.stats_changed，调用 get_peer_stats(1)。rtt_msec 为 ENet 原生平均往返时间，jitter_msec 为原生 RTT 波动估计；不是单程延迟或准确丢包率。age_msec 表示最近收到该直接对端的有效会话包距今多久，远端统计还计入房主汇总传输后的本地等待时间；它不是 ENet 某一次 RTT 样本的时间戳。校时消息自然提供空闲时的通信活跃度，不再另发心跳。首次缓存建立前显示测量中，超过 3 秒没有会话包或汇总过期显示无响应；较高 RTT/波动显示波动。框架不伪造“0 ms”，也不把应用层无响应直接当作断线，最终断线仍由 ENet 判定。

订阅 api.player_disconnected(player_id, peer_id)；玩家 connected 已为 false。玩法停止该玩家的输入与网络实体，并按规则决定 withdrawn 排名。players_changed 继续可用。加载期间断线由框架取消，不继续等待一个永远不会 ready 的端点。回到大厅时移除断线名额。房主离开时关闭所有作用域与相关媒体。

## 网络实验

主菜单“连接测试”下方的“网络实验”进入独立设置页。房主侧与客机侧是本机的两份配置，分别用于下次创建和加入房间，不会远程修改其他人的设置。默认关闭；每侧可设置启用、额外发送延迟（0–2000 ms）和随机发送丢包率（0–100%）。草稿显式保存后才写入 `core/config/settings.json` 的 `network_lab` 节；字段为 `host.enabled`、`host.delay_msec`、`host.loss_percent` 及对应 `client.*`。返回不自动保存，恢复默认也需保存。

模拟在 ENet 下方的本进程 UDP 中转层执行，只处理本机发出的数据报：房主向客机发送、客机向房主发送。接收方向正常转发。若房主与客机都增加 100 ms，链路 RTT 约增加 200 ms；单侧增加 100 ms 时约增加 100 ms。队列由主循环处理，实际等待还受帧率与系统调度影响。随机丢包针对整个 UDP 数据报，可靠重传、ACK、握手、原生 RPC、Spawner/Synchronizer、语音和校时均经过同一路径。可靠消息不会因为应用层直接丢弃而永久消失，仍由 ENet 重传或报告超时。高丢包/高延迟可能使现有连接或准备超时正常触发；100% 丢包用于模拟完全不通。

关闭时保持原来的直连路径。开启时房主仍公布选定的外部地址/端口，内部 ENet 监听回环临时端口；客机仍填写真实房主地址。连接测试和监听测试工具不受该设置影响。状态角标显示“实验”，提醒本机已启用模拟。Tab 显示实际 ENet RTT/可靠包丢失估计，不伪造为设置值；原生丢失率的统计范围和平滑使其不必等于随机丢包概率。

离开时关闭中转、清空所有延迟包；不把旧连接的数据转发到下一局。最多保留 32 条 UDP 地址映射，闲置 30 秒回收；延迟队列上限为 8192 包/16 MiB，超过上限明确终止实验连接并报告错误，不静默制造额外丢包。当前只做静态检查，尚未完成运行、真实弱网与 1920×1080 人工界面验收。
