# 生命周期与通信

## 运行顺序

创建实例 API 和处理器 → 实例化 → 入树前 setup → 入树初始化 → 显式 mark_ready →
所有在线必要端就绪 → party_start → finish / fail → 提交或取消 → 关闭 API →
party_stop → LIFO 清理 → 释放场景。

`mark_ready()` 和 `party_start()` 只表示框架的技术准备屏障，不表示玩家已阅读规则或手动准备。
`get_preparation_status()` 返回本作用域的 `session_id`、`scope_id`、`phase`、
`required_peers` 与房主确认的 `ready_peers`。技术就绪包含游戏初始化、设置生效和规则校验；
开始后保留本次屏障的端点快照，关闭 API 后返回空字典。内容可读取该诊断快照，不能修改框架状态。
游戏如需玩家确认、规则页或倒计时，应自行实现（或选用协议的可选资源），并在确认流程完成前
保持输入、计时、音乐和模拟停止。不得将手动点击伪装成 `mark_ready()`，也不应让30秒技术超时计作阅读超时。

准备阶段的 ready 后续处理排队执行，避免从 _ready 重入 party_start。
一轮只有一个终态；旧局消息不交给新局。每局参与者名单固定，断线仅更新 connected。

一个顶层大游戏可以拥有一个前台小游戏，未参赛者全部加载并观战。
房主即使观战也继续执行房主玩法逻辑。加载失败或超时取消本轮；全部参赛者退出取消本轮；
房主退出结束会话。没有运行中加入、重连、迁移或多层嵌套。

## 通信声明

内容检查分为加入与开始两个阶段：加入时核对框架名称/版本、当前房间的协议、主游戏及必需依赖/形象包；开始时核对所选小游戏池及完整依赖。按包 ID 定位、精确匹配版本，名称使用 manifest 原始值。无关的额外安装包不要求同步。缺包或版本差异显示具体条目；下载完成后重启安装，再手动加入。房间规则或成员形象更新后重新确认；内容确认、玩家准备与场景 mark_ready 分别表达不同状态，不互相代替。

内容通信无需 manifest 流声明。直接使用 Godot `@rpc`，或发送时指定 `PartyNet` 的可靠性与逻辑通道。参见[内容网络通信指南](networking.md)及[签名参考](reference.md)。

基础值、数组、字典及已支持的 Godot 值可发送；Node、Resource、Callable、Signal 和 RID 不能发送。自定义编码使用 PackedByteArray。框架不提供自动预测、回滚或插值。

原生通道可用 0–7。框架控制与 Godot 原生生成/销毁共用可靠通道 0，保持销毁先于作用域关闭；高频自定义原生 RPC 推荐用 1–7。8 为内容下载可靠通道，9 时钟/延迟，10 语音，11–22 为 PartyNet 内部通道，内容不得直接占用。PartyNet 的 `channel=0..3` 是逻辑通道，框架按可靠性映射到内部通道。不同通道、不同传输模式之间不保证顺序；topic 不产生独立网络通道。

原生节点位于稳定实例根路径。不要替换框架 MultiplayerPeer 或另建全局 MultiplayerAPI。原生消息不受 PartyNet 的作用域过滤承诺约束；关闭时停止发送、定时器及同步器，并在节点仍存在时完成原生销毁。

技术准备还等待首次主机时钟同步。大厅删除掉线玩家；局内保留名单并标记 connected=false，发出 `player_disconnected(player_id, peer_id)`，排名由玩法决定；加载阶段掉线取消加载。房主离开结束会话，未实现断线重连或房主迁移。延迟直接读取 ENet 原生 RTT，不额外发送测速探测；客机校时请求单独保留。ENet 判定掉线，高延迟不改变游戏模拟速度。

父实例在子游戏期间仍能处理协议消息，但持久业务状态冻结，最终变更进入 reducer。

设置 runtime.enter 在玩法入树前执行，attach_view 在入树后执行；最终 READY 同时要求游戏就绪、设置就绪和规则摘要一致。详细约束见 [配置生命周期](configuration.md)。


## 提前关闭

party_stop 可以在 setup 前、setup 后但入树前、正常运行后以及重复关闭时调用。只清理由本实例已创建或激活的资源；入树前不能读取 @onready 引用。正常初始化仍严格检查必需场景引用。停止输入、音频、计时和网络发送，并使延迟回调失效。继续使用 PartyAPI.on_close 与内容自己的停止方法，关闭保持 API 先关闭、内容停止、LIFO 清理、移出场景的顺序。
