# 源码与 PCK 内容包

## 声明、版本与包身份

作者清单基础字段为 `name`、`kind`、`package_version`、`framework_version`、`remark`、`supported_languages`，以及需要时的 `dependencies`。曲库资产包额外声明 `special_type` 和 `songs`。备注允许为空。`supported_languages` 是作者声明的支持语言数组，当前统一为 `["zh-CN"]`，不根据已有翻译文件推断完整语言支持。身份来自目录，形象包归属来自协议父目录。所有现有包从 `0.0.1` 开始；当前框架版本在 `core/framework_version.gd`，不使用或修改 Godot 项目版本。

版本必须是没有前导零的三段非负整数；每段不超过 GDScript int64 上限。依赖值仅支持精确三段版本、`~` 和 `^`，不支持预发布、构建后缀、通配符和范围组合。`~0.0.1` 接受 `0.0.2`、`0.0.10`，不接受 `0.1.0`；`^0.0.1` 只接受 `0.0.1`；`^0.1.2` 接受同一 `0.1` 下不小于 `0.1.2` 的版本；`^1.2.3` 接受小于 `2.0.0` 且不小于下限的版本。框架版本始终精确匹配。没有独立 API、联机协议或引擎版本兼容门槛；构建不自动升版本。

源码位于 `games/{protocols,maingame,minigame,assets}/<id>/`，形象位于 `games/protocols/<协议ID>/avatars/<id>/`。导出工具默认沿用相同类别目录，但运行时不要求这些物理目录名。每个包是一个含 `content.pck.json` 的文件夹，可放在安装根目录或分组文件夹内；也支持当前协议内 `avatars/` 布局。包 ID 和形象归属由生成的描述识别，移动整个包目录不改变身份。个人配置仍使用原有按类别和 ID 划分的固定路径，与内容文件夹位置分离。资产包不依赖其他内容包。

源码 ZIP 统一命名为 `<id>.zip`；导入形象源码时，目标目录指定为所属协议的 `avatars/`，由目录恢复协议归属。

工具从作者清单、轻量 `definition.gd` 和适配器提取目录元数据，作者仍只维护 `manifest.json`。取消整包 Hash 生成与校验，导出时生成随机 `build_id` 标识本次内容构建；它不证明文件字节一致。复制同一构建给不同平台会保留标识，分别重新导出会产生不同标识。当前格式不兼容旧 Hash 描述，需要重新导出。

`content.pck.json` 保存身份、声明、玩法定义、依赖和以下相对路径：

- `packs`：一个或多个 PCK 路径，可自由命名、拆分并放入子文件夹。默认工具仍生成单个 `content.pck`。
- `resource_index`：资源路径、UID 和全局脚本类型清单，默认 `resources.json`；首次使用包时才读取。
- `settings`：构建时生成的设置 schema 与各语言标签快照，默认 `settings.json`。大厅计算规则、默认值和人数无需运行小游戏代码。
- 可选 `preview`：最大边长 256 像素的独立预览图。
- `payload_files`：所有正式分发文件，不包含描述自身；`external_files` / `external_directories` 保留正式外置数据及空目录。

拆分 PCK 时同时更新 `packs` 和 `payload_files`，资源索引仍覆盖这些 PCK 的并集。PCK 内的逻辑 `res://games/...` 路径、UID、包归属和依赖契约保持不变。物理文件夹自由组织不表示可以任意改变脚本引用或覆盖框架资源。运行时保留版本、依赖、路径、UID 和类型名冲突检查；不设置脚本安全沙箱。

## 启动与首次使用

主菜单扫描小型描述，检查框架与依赖可用性；不打开 PCK、不读取完整资源索引，不加载协议运行脚本或游戏场景。编辑器直接扫描源码清单和轻量定义，不构建、不挂载分发包。协议的声明也移到 `definition.gd`，运行入口仍为 `protocol.gd`。主菜单昵称直接读取本地资料。

创建或加入房间时加载选中的协议及主游戏大厅，连同它们声明的必需依赖；不会因为游戏池包含某个小游戏就挂载它。通用设置从独立元数据读取，作者自定义设置面板和校验代码在实际使用时加载。浏览列表只建立可见行，预览图缓存最多 32 张。开始某个玩法时才挂载其 PCK 与条件依赖，用 Godot 后台资源加载接口读取 `game.tscn`，完成后在主线程实例化。进度条反映 Godot 资源读取进度；实例化、脚本初始化和 GPU 首次资源准备仍可能占用主线程。

联机继续区分内容确认与场景就绪：所有必需客户端报告准备完成后，房主才开始玩法。退出房间或取消加载会使旧请求失效，后台完成的旧场景不得进入场景树。Godot 没有在这里使用的 PCK 卸载机制；退出玩法释放场景引用，已挂载的包保持挂载至进程结束，不承诺逐局卸载所有缓存。

安装与更新属于独立阶段：移动端首次安装内置 ZIP、以及启动时应用排队更新，仍需复制正式文件，但不加载其中游戏资源。批次结构、版本和依赖检查通过后事务替换，失败回滚。已安装且未使用的包不会因启动而读取全部数据。未选中且无效的描述记为不可用；实际请求的缺失文件或加载错误明确失败。运行期间不热替换，更新下次启动生效。

## 入房内容同步

加入时比较当前房间协议、主游戏和必需依赖/形象；开始时加入所选小游戏及其条件依赖。发布版比较所需包 ID、实际版本和 `build_id`，额外安装包不参与。不同版本或不同构建需要同步；手工改变文件而保留标识不会被字节校验发现。框架版本不同需手动更新框架，发布平台不作为互联限制。

编辑器只用于同步源码的内部多实例测试；双方比较框架版本、包版本和依赖，不携带构建标识、不自动构建或下载。编辑器与发布版通过 `source` / `pck` 模式明确拒绝互联。`--party-pack-dir=<目录>` 仅指定发布版安装集。

ENet 保留有界分块、取消、路径和长度校验；内容同步提议读取载荷长度，实际下载时才读取字节。下载做结构检查后排队，完成后需要重启，不自动重连。个人 `config/` 和存档不参与正式载荷，不被更新覆盖；旧描述中退役的正式文件随更新事务删除。

## 可视化 Windows 导出

编辑器打开“项目 → 工具 → GodotParty：导出 Windows 可玩包”。界面分别列出核心、协议、形象包、资产包、主游戏和小游戏；各类包均可独立勾选，再选择输出目录。点击开始导出后显示阶段进度条、当前阶段、错误和构建日志目录。进度按实际完成的阶段计数，不表示剩余时间；iOS 云端排队、构建及下载使用不定进度显示，全部产物发布成功后才完成。导出由独立 PowerShell 进程运行，关闭窗口、卸载插件或退出编辑器均不等待构建；任务继续完成，结果保存在任务目录的 `job-result.json`，完整记录在 `export.log`。同一编辑器内重开窗口可继续查看正在运行的任务。空闲时每次打开窗口都会扫描 `games/{protocols,maingame,minigame,assets}/<id>/manifest.json`，形象包扫描 `games/protocols/<协议ID>/avatars/<id>/manifest.json`。所有类别的列表名称直接读取声明的 `name`，不经过翻译替换。目录 ID 继续用于依赖引用和导出安装路径。

勾选内容会自动补齐满足范围的依赖、所属协议以及小游戏适配器的协议和依赖；自动勾选项标注“依赖”。导出会包含所选小游戏的全部已声明适配器依赖。主游戏的小游戏池由房主在运行时选择，导出主游戏不会自动打包所有候选小游戏。取消核心后，协议、形象、资产、主游戏和小游戏均可独立导出为安装目录（含各包 PCK、描述及正式外置数据），只自动补齐必需依赖，不附带其他类别的全部内容。勾选核心时同时构建 Windows x64 EXE，也可只导出核心。

原版协议包含两个独立形象包。godot_party_default_avatars_2d 提供六个 2D 头像，godot_party_default_avatars 提供 Cube 3D 占位。包均位于 protocols/<协议ID>/avatars/<包ID>/，默认依赖会一起勾选。旧玩家资料中的协议内头像引用需在个人资料界面重新选择并应用。

选择项目外目录，或本项目 tmp/releases/ 下的目录（验收产物可放 tmp/test/）。后台使用 PATH 上的 godot 和匹配的 Windows 模板，在 tmp/exports/ 下构建核心副本、日志和中间产物。核心副本排除内容、开发插件、个人 JSON 配置和存档，并关闭场景文本到二进制转换以保留嵌套 UI。不会启动项目升级。

全部构建成功后才写入输出目录。已有 EXE 和描述中列出的正式载荷成套更新；个人配置和存档保留；退役载荷文件进入同一回滚事务。发布失败会回滚已覆盖文件，备份保留在构建目录。导出期间请关闭目标目录中的游戏；同一目标目录同时只允许一次导出。

完整安装目录可直接通过 Windows 文件资源管理器合并。也可在内容管理中选择含描述的包文件夹；单独一个 PCK 不提供识别所需的目录信息。首次分发时不要附带测试启动生成的 core/config/settings.json，避免复制 player_id。应用偏好后生成的 JSON 位于各包 config/ 下，退出游戏后可以手动编辑。

`core/dev/export_job.ps1` 是窗口的后台入口，接收 `RequestPath` 指向的 JSON，按平台调用本地 `export_release.ps1` 或 iOS 云导出后端。命令行也建议调用该入口，以保留任务锁和完成结果。请求包含 core 布尔值、output 绝对目录和 packages 包 ID 数组。export_windows_host.ps1 可单独构建核心；export_windows_minimal.ps1 是原版轮换与阿瓦隆的预设，复用同一后端和依赖计算。运行后仍需检查正式菜单、设置和实际开局；导出成功不等于多人或外网验收。

## 可视化 Android 导出

通常使用 Godot 编辑器设置中的 SDK 路径。若运行中的编辑器反复写回旧 SDK 配置，可在本机 `tmp/local/android_export.json` 写入 `{"android_sdk_path":"F:/AndroidSDK"}`。可视化导出器会提前检查该目录，并在隔离的 APK 导出进程内应用此路径；该文件不提交、不进入可玩包，也不增加导出窗口选项。没有此文件时仍使用编辑器设置，存在但无效时明确失败，不自动猜测 SDK 位置。

编辑器打开“项目 → 工具 → GodotParty：导出 Android 可玩包”。仍只需勾选内容和选择输出目录，依赖选择规则与 Windows 相同。勾选核心会生成 `GodotParty.apk`，同时生成 `GodotParty-content-android.zip`；不勾选核心则只生成内容 ZIP，用于单独更新所选协议、形象、资产、主游戏或小游戏。后端请求增加 `platform: "Android"`，省略时仍导出 Windows。

Android 的 `version/name` 和 iOS 的 `application/short_version` 从作者维护的 `project.godot` 的 `application/config/version` 读取，只写入隔离构建副本，不修改项目版本或框架版本。Android `version/code` 继续由 Android 预设维护，iOS 构建编号由工作流运行编号提供。仅勾选核心时仍产生可安装的空内容 ZIP，跳过内容资源导入。

当前 APK 是 ARM64、横屏、调试签名的测试包，使用本机 Godot 已配置的 Android SDK、Java 和匹配导出模板。导出器在隔离工程中导入 Android 资源，使用 Compatibility 渲染器，并启用屏幕触摸模拟鼠标左键；不会把触摸变成键盘操作，也不提供虚拟摇杆。需要键盘或鼠标右键的小游戏仍须另行适配。初版选择小游戏轮换与竞拍大师。

APK 内置所选共享内容 ZIP；首次启动在应用私有存储中安装各包，首次实际使用时才挂载所需 PCK 和注册 `class_name`。每个新 APK 构建首次运行会更新内置内容，已有 config/ 保留，正式外部文件随包事务更新；候选集合先通过版本、依赖与载荷结构检查，再安装。独立 ZIP 也使用相同目录与校验，不将配置打包。Android 导出同样生成包含两种纹理导入格式的 PCK，可直接分发给 Windows 客机；框架 EXE/APK 仍分别构建。

Android 不使用 Windows 文件资源管理器直接合并安装目录。在“内容包”中选择 Android 内容 ZIP，完全退出应用再打开后生效，不热替换正在使用的 PCK。原生文件选择器要求 Android 10 或更新系统；系统配置 JSON 可在此导出、编辑并导入，玩家身份保留。游戏偏好仍通过游戏内设置修改。覆盖安装 APK 时需保持包名与签名；卸载或清除应用数据会删除配置。

APK 构建成功仅证明导出流程完成。真机验收需检查首次启动、创建/加入房间、竞拍大师触摸操作及再次启动后的配置保留。

## 外置文件与目录

正式原样数据固定放在包内 `external/`，不在作者 manifest 中逐项声明。目录不存在表示没有外部数据。工具按包的 `export_ignore.txt` 规则生成 `external_files` / `external_directories` 索引，保留未排除的空目录；导入映射、UID 和 `.gdignore` 不作为正式外部文件。路径必须满足可移植规则，链接不允许发布。个人可编辑资料、偏好和存档必须放在此目录外。以霓虹节拍为例的读取方式与曲目分发方案见 [外部资源指南](external_resources.md)。

游戏使用 `api.get_external_path("external/maps/default.json")` 获取源码包或发布版安装产物的物理路径。FileAccess/DirAccess 可以直接使用；PNG、音频等采用运行时文件加载 API。普通预加载资源留在 PCK 中。发布更新会替换并移除旧描述中的退役文件；config/ 不受影响。

普通资源保留 `.import`、`.uid` 和运行时导入产物，已有有效重映射时不重复携带原始媒体；源码 ZIP 保留原始素材和导入参数。编辑器运行不依赖分发缓存；重新导出时使用当前打包代码，无独立构建修订计数。包的版本号仍由作者明确维护。

## 可视化 iOS 云导出

编辑器打开“项目 → 工具 → GodotParty：导出 iOS 可玩包”。仍只需勾选内容和选择下载目录。勾选核心生成 `GodotParty-iOS-SideStore.ipa` 与 `GodotParty-content-ios.zip`；不勾选核心只生成内容 ZIP。每次下载存入所选目录中的 `ios-<提交版本>-<运行编号>/`，附带 `build-info.json` 和安装说明，不覆盖其他构建。

Windows 本机需要 Git、GitHub CLI 和 PATH 上的 Godot；先运行 `gh auth login -h github.com`，账户需要该仓库 Actions 的运行权限。后端 `core/dev/export_ios_cloud.ps1` 使用 origin 指向的 GitHub 仓库，只构建已推送的当前 HEAD；未提交修改不会进入云端，尚未推送的提交明确失败。窗口显示提交、工作流链接及构建阶段；详细记录在本次 `tmp/exports/` 目录。修改源码或内容后，应先提交并推送相关小游戏子模块，再推送主仓库引用。

`.github/workflows/build-ios.yml` 在 macOS/Xcode 上检出指定提交及其子模块，安装与本机 Godot 相同版本的编辑器和 iOS 模板。`core/dev/build_ios.py` 与 Android 后端直接共用 `core/dev/export_mobile_content.ps1` 内容导出入口（不调用 Android APK 导出器），自动补齐依赖、重新导入资源，再构建独立的 iOS 框架工程。框架声明 `ios`，使用 Compatibility 渲染、横屏、触摸模拟左键；左上角 Esc 第一次触碰只显现，再点击才发送 Esc。移动端玩法仍须实际适配触摸与设备能力，包版本检查不代替真机验证。

IPA 面向 ARM64 iPad/iPhone，仅带 ad-hoc 签名，必须导入 SideStore 重签安装，不能直接安装，也不是 TestFlight/App Store 包。本流程不接收 Apple 证书。GitHub 保留可玩产物 14 天、构建日志 7 天；构建失败时查看运行链接中的诊断产物。

iOS 配置和内置内容安装到应用私有存储，保留已有玩家配置，正式外置文件按事务更新；更新时保持应用标识和签名身份。卸载或清除应用数据会丢失配置。内容 ZIP 导入后需要重启，不热替换 PCK。云端结构和编译检查不代替 iPad 真机触摸、文件选择器、房间创建及多人联网验收。


## 统一资源收集边界

内容作者在包根目录使用 `export_ignore.txt` 决定发布排除项；有文件时完整替代默认规则，空文件表示不使用默认排除项。没有文件时使用 `core/content/default_export_ignore.txt`，默认排除各层 `authoring/`、`prototype/`、`tmp/`、隐藏项及常见临时备份。规则采用 Git ignore 模式，支持 `!`、`**`、字符组、转义及后匹配优先；固定区分大小写，只读取包根一个规则文件。精确语义与示例见 [作者导出规则](external_resources.md#export_ignoretxtgit-ignore-语法)。

`core/content/party_export_files.gd` 统一源码 ZIP、PCK 暂存和外置数据过滤；PowerShell 的 `core/dev/export_source_files.ps1` 遵守相同规则。三平台共用该内容流程，Android 与 iOS 共用 `export_mobile_content.ps1` 生成内容 ZIP。收集器只保留必要技术边界：Git/引擎缓存、包内个人 `config/` 不发布，协议不包含独立 avatars 子包，链接路径明确失败。普通资源的 `.import/.uid` 保留；排除其原文件时伴随文件也排除。

内容暂存完整复制作者的导入设置，再由所选 Godot 在干净工程中生成目标资源。声明的外置文件只由外置流程复制一次；构建专用 `.gdignore` 或 Keep File 导入标记阻止它们被再次转换，标记不随外置文件发布。可玩 PCK 的普通导入资源只保留重映射与运行产物；原样文件按其使用方式保留，不按音频/图片扩展名盲目删源文件。

不发布的开发资源建议放入包内 `authoring/`，由默认规则或作者规则排除；不使用 `.gdignore` 隐藏开发目录。`.gdignore` 只控制 Godot 导入，不是发布排除配置；`.gitignore` 也不决定打包范围。作者自定义规则时应显式保留需要的排除项，正式资源不得引用被排除文件。具体分类和音效/图片单一正式路径规则见 [原版资源开发规范](authoring.md#原版资源开发与发布目录)。

## 资产包

资产包位于 `games/assets/<id>/`，默认导出到 `assets/<id>/`，通过 `content.pck.json` 识别。目录名是 ID；作者 manifest 必须含 `name`、`kind: "assets"`、`package_version`、`remark`、`framework_version`、`supported_languages` 六个字段，框架版本精确匹配。可选 `special_type` 标记资产包类型；霓虹节拍曲库声明 `special_type: "rhythm_library"` 和 `songs` 曲目资源相对路径数组。结构与制作方式见 [曲库资产包](external_resources.md)。资产包可包含代码、场景、素材、文档等公共内容，不声明平台、入口、设置或其他内容依赖；包内互相引用，包外仅引用框架公开内容。资产包之间不得相互引用。

协议和游戏用原有 dependencies 声明资产包的版本范围，在编辑器直接引用资产包路径。导出自动补齐依赖，PCK 仅收集所属包的文件与导入产物；发布版下载、排队安装和重启规则保持一致。资产包源码 ZIP 文件名必须是 `<id>.zip`，导入时据此恢复目录身份。PCK 描述仍由工具生成，不增加作者维护字段，使用相同构建标识与按需加载流程。

小游戏轻量定义可声明 `asset_types`，由房主在房间依赖中纳入匹配类型的候选资产包，客机仅使用房主集合。此过程不挂载 PCK；首次加载所选资源才激活。导出时由作者显式选择要分发的可选曲库，不自动打包所有本地曲库。

发布版联机比较框架版本及所需包的实际版本和构建标识；新增包后需要重新导出并重启。编辑器新增源码包后重新运行即可，内部联机不构建分发包。

原版 UI 0.0.1 提供准备/结算展示视图、HUD、资料编辑视图、玩家光标、字体，以及数字动画、轮换大厅、大富翁 UI和未被框架使用的 Ambient Reveal 扩展组件。原版协议保留准备/结算协调及结果校验；资料适配器向 UI 注入协议标识、颜色和颜色名称。框架自身启动、内容管理与下载 UI 不依赖资产包。


## 构建和临时目录

纯依赖选择在 core/content/party_content_selection.gd；显式导出的隔离导入与 PCK 写入在 core/dev/party_shared_pack_builder.gd。发布核心不包含或预加载 core/dev。编辑器启动不加载构建器；发布版运行期间只分发已冻结的安装产物。批量选定集合只暂存、导入一次，再按每包归属写独立 PCK。隔离 PCK 构建工程串行导入资源，避开本次全量验证中重复崩溃的并行字体导入路径。头像包随所属协议一起判定可用性；协议不可用时，其头像也不挂载或注册脚本类型。

内容请求、准备、数据块、完成及取消使用 CONTENT_CHANNEL=8，可靠性由 ENet 提供。每客户端一次下载一个文件，32 KiB/块、8 块在途；房主每客户端队列最多 16 项，每帧轮流处理最多 16 块。任务 ID 隔离重试与取消，接收校验文件及偏移。复用文件句柄，约 1 MiB 或文件结束刷新。ZIP 写入和入队复制按约 1 MiB 分帧，显示下载、整理文件、等待重启状态。

构建成功并验证产物后删除本次 tmp/content_build 工作目录；失败保留日志，删除可再生源码及导入副本。下载成功入队、失败或明确取消时关闭句柄并回收本任务 tmp/content_download；完整待安装 tmp/content_update.zip 保留至启动安装成功，入队失败不改动此前任务。旧 tmp/content_distribution 不再参与编辑器启动。不要在任一实例运行时清理其他实例的遗留目录；离线清理入口为 core/dev/clear_content_work.ps1，保留 tmp/local 与所有包 config。根 assets/ 只存安装内容并由 Git/Godot 忽略；games/assets/ 是版本控制中的开发源码。

移动端在同一次任务内复用内容工程已经生成的核心资源导入产物、重映射和 Godot 原生校验元数据，核心工程仍正常扫描、验证并补齐缺失导入。仅复用核心和图标，不复制内容包缓存、编辑器文件系统索引或跨任务缓存；只导出核心时正常执行首次导入。核心源码复制使用批量收集和直接文件 API，内容 ZIP 使用快速压缩以缩短打包耗时，体积可能略增。

### 可玩包导出任务目录

每次导出使用一个新的任务目录，包含 `request.json`、`progress.json`、阶段日志、`export.log` 和 `job-result.json`。进度文件以原子替换写入，窗口每半秒读取，失败时停止进度并保留实际失败原因。Windows 内容工作区通过 `--workspace` 放入本任务 `content_work/`；构建器在清理成功的导入副本前保留导入和打包日志。失败日志、请求和 `previous/` 回滚备份不会被自动删除。

任务完成后可运行 `core/dev/clear_export_work.ps1 -JobDirectory <本次任务绝对目录>`，清理该任务的核心/移动源码和导入副本。该入口只接受项目 `tmp/` 下已有完成结果的任务，使用任务锁拒绝清理仍在执行的导出，预先拒绝目录链接和越界路径；保留正式输出、`build/` 成品副本、内容 ZIP、日志、请求、结果及回滚备份。可在编辑器仍打开时清理已完成的其他任务，不清理正在运行的游戏或其他任务缓存。
