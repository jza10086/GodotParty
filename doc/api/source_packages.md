# 源码与 PCK 内容包

## 声明、版本与包身份

作者清单只有 `name`、`kind`、`package_version`、`framework_version`、`remark`、`supported_languages`，以及需要时的 `dependencies`。备注允许为空。`supported_languages` 是作者声明的支持语言数组，当前统一为 `["zh-CN"]`，不根据已有翻译文件推断完整语言支持。身份来自目录，形象包归属来自协议父目录。所有现有包从 `0.0.1` 开始；当前框架版本在 `core/framework_version.gd`，不使用或修改 Godot 项目版本。

版本必须是没有前导零的三段非负整数；每段不超过 GDScript int64 上限。依赖值仅支持精确三段版本、`~` 和 `^`，不支持预发布、构建后缀、通配符和范围组合。`~0.0.1` 接受 `0.0.2`、`0.0.10`，不接受 `0.1.0`；`^0.0.1` 只接受 `0.0.1`；`^0.1.2` 接受同一 `0.1` 下不小于 `0.1.2` 的版本；`^1.2.3` 接受小于 `2.0.0` 且不小于下限的版本。框架版本始终精确匹配。没有独立 API、联机协议或引擎版本兼容门槛；构建不自动升版本。

源码位于 `games/{protocols,maingame,minigame,assets}/<id>/`，形象位于 `games/protocols/<协议ID>/avatars/<id>/`。安装目录分别是 `protocols/`、`maingame/`、`minigame/`、`assets/`，形象保留所属协议层级。每包生成 `content.pck`、`content.pck.json` 和可选 `external/`。资产包不依赖其他内容包。

源码 ZIP 统一命名为 `<id>.zip`；导入形象源码时，目标目录指定为所属协议的 `avatars/`，由目录恢复协议归属。

工具生成的描述记录作者声明、从入口/适配器提取的玩法定义、依赖、路径与 UID 索引、全局脚本类型，以及唯一的 `package_hash`。作者不维护第二份清单。Hash 是实际 PCK、正式外部文件和描述内容的 SHA-256；描述排除自身 `package_hash`，对象键排序，路径数组和类型清单确定性排序，以紧凑 UTF-8 JSON 编码。相对路径使用 `/` 且保留大小写；元数据、每个路径和文件字节均带八字节小端长度前缀。没有逐文件 Hash 表。字体、导入参数、UID 和许可证按正式内容保留。

## 启动与更新

每次启动先合并已安装包、内置更新及待安装更新，形成候选最终集合。每个候选包只计算一次实际 Hash，同时检查框架、依赖范围、目录、文件/UID/类型名冲突。待安装批次全部通过后才事务替换，失败保留旧包；成功后复用本次结果挂载和注册。未选中且无效的旧包记为不可用，不阻塞无关游戏。所选适配器的条件依赖和不可用原因缓存于 Catalog。

启动后冻结包的 `{id, version, hash}`。菜单、入房、开始只读缓存，不重扫磁盘、不重算 Hash、不做资源/设置/翻译/继承关系预审。资源、脚本和设置在实际使用处加载，失败正常暴露。运行期间不热替换包，更新在下次启动生效。

编辑器在加载玩法前确定构建产物。`tmp/content_distribution/` 根据实际源码、导入参数、核心构建代码及引擎构建输入生成缓存键；源码改变但版本不变也会生成新一代 PCK。实际运行、启动校验和房主分发使用同一代产物。已安装包默认使用安装产物；内容来源选择 `source` 表示本次源码构建产物，`pck` 表示安装产物，切换需要重启。`--party-pack-dir=<目录>` 使用指定安装集，不混入编辑器源码。客户端接收房主产物，不能假设两台编辑器分别构建的包相同。

## 入房内容同步

加入时比较当前房间协议、主游戏和必需依赖/形象；开始时加入已选小游戏及其条件依赖。只比较所需包 ID、实际版本和 Hash，额外安装包不参与。同版本不同 Hash，以及范围兼容但实际版本不同，都必须同步。框架版本不同需要手动更新框架；不根据系统平台声明拦截内容。

沿用 ENet 的有界分块、取消、路径和长度校验。下载只接收、做结构检查和排队，不在运行中重新计算包 Hash；启动时验证整批候选。完成提示“更新后需要重启”，不热替换、不自动重连。个人 `config/`、存档和可编辑资料不进入正式包身份，也不被更新覆盖；正式 `external/` 随包替换并删除退役文件。

房主开始时仍等待所有必要客户端完成内容确认和准备。缺失或不同内容列出当前/所需版本；取消检查保留完整待安装包，取消未完成传输清理其私有临时目录。框架内容具备普通 Godot 脚本能力；兼容和完整性检查不是代码安全沙箱。

## 可视化 Windows 导出

编辑器打开“项目 → 工具 → GodotParty：导出 Windows 可玩包”。界面只需勾选核心、协议及形象包、主游戏、小游戏，再选择输出目录。点击开始导出后显示进度、错误和构建日志目录。每次打开窗口都会扫描 `games/` 下各类型包目录；小游戏来自 `games/minigame/<id>/manifest.json`，列表名称直接读取声明的 `name`，不经过翻译替换。目录 ID 继续用于依赖引用和导出安装路径。

勾选内容会自动补齐满足范围的依赖、所属协议以及小游戏适配器的协议和依赖；自动勾选项标注“依赖”。导出会包含所选小游戏的全部已声明适配器依赖。主游戏的小游戏池由房主在运行时选择，导出主游戏不会自动打包所有候选小游戏。仅勾选内容可生成独立更新包，勾选核心时同时构建 Windows x64 EXE。

原版协议包含两个独立形象包。godot_party_default_avatars_2d 提供六个 2D 头像，godot_party_default_avatars 提供 Cube 3D 占位。包均位于 protocols/<协议ID>/avatars/<包ID>/，默认依赖会一起勾选。旧玩家资料中的协议内头像引用需在个人资料界面重新选择并应用。

选择项目外目录，或本项目 tmp/releases/ 下的目录（验收产物可放 tmp/test/）。后台使用 PATH 上的 godot 和匹配的 Windows 模板，在 tmp/exports/ 下构建核心副本、日志和中间产物。核心副本排除内容、开发插件、个人 JSON 配置和存档，并关闭场景文本到二进制转换以保留嵌套 UI。不会启动项目升级。

全部构建成功后才写入输出目录。已有 EXE、content.pck 和 content.pck.json 成套更新；个人配置和存档保留；正式 external/ 文件替换，旧描述中已退役的正式外部文件进入同一回滚事务。发布失败会回滚已覆盖文件，备份保留在构建目录。导出期间请关闭目标目录中的游戏；同一目标目录同时只允许一次导出。

完整安装目录可直接通过 Windows 文件资源管理器合并。形象包保留所属协议路径。首次分发时不要附带测试启动生成的 core/config/settings.json，避免复制 player_id。应用偏好后生成的 JSON 位于各包 config/ 下，退出游戏后可以手动编辑。

core/dev/export_release.ps1 是窗口使用的同一后端，接收 RequestPath 指向的 JSON。请求包含 core 布尔值、output 绝对目录和 packages 包 ID 数组。export_windows_host.ps1 可单独构建核心；export_windows_minimal.ps1 是原版轮换与阿瓦隆的预设，复用同一后端和依赖计算。运行后仍需检查正式菜单、设置和实际开局；导出成功不等于多人或外网验收。

## 可视化 Android 导出

通常使用 Godot 编辑器设置中的 SDK 路径。若运行中的编辑器反复写回旧 SDK 配置，可在本机 `tmp/local/android_export.json` 写入 `{"android_sdk_path":"F:/AndroidSDK"}`。可视化导出器会提前检查该目录，并在隔离的 APK 导出进程内应用此路径；该文件不提交、不进入可玩包，也不增加导出窗口选项。没有此文件时仍使用编辑器设置，存在但无效时明确失败，不自动猜测 SDK 位置。

编辑器打开“项目 → 工具 → GodotParty：导出 Android 可玩包”。仍只需勾选内容和选择输出目录，依赖选择规则与 Windows 相同。勾选核心会生成 `GodotParty.apk`，同时生成 `GodotParty-content-android.zip`；不勾选核心则只生成内容 ZIP，用于单独更新小游戏。后端请求增加 `platform: "Android"`，省略时仍导出 Windows。

当前 APK 是 ARM64、横屏、调试签名的测试包，使用本机 Godot 已配置的 Android SDK、Java 和匹配导出模板。导出器在隔离工程中导入 Android 资源，使用 Compatibility 渲染器，并启用屏幕触摸模拟鼠标左键；不会把触摸变成键盘操作，也不提供虚拟摇杆。需要键盘或鼠标右键的小游戏仍须另行适配。初版选择小游戏轮换与竞拍大师。

APK 内置所选共享内容 ZIP；首次启动在应用私有存储中安装各包，再挂载 PCK 和注册 `class_name`。每个新 APK 构建首次运行会更新内置内容，已有 config/ 保留，正式外部文件随包事务更新；候选集合先通过启动版本、依赖与实际 Hash 校验，再安装。独立 ZIP 也使用相同目录与校验，不将配置打包。Android 导出同样生成包含两种纹理导入格式的 PCK，可直接分发给 Windows 客机；框架 EXE/APK 仍分别构建。

Android 不使用 Windows 文件资源管理器直接合并安装目录。在“内容包”中选择 Android 内容 ZIP，完全退出应用再打开后生效，不热替换正在使用的 PCK。原生文件选择器要求 Android 10 或更新系统；系统配置 JSON 可在此导出、编辑并导入，玩家身份保留。游戏偏好仍通过游戏内设置修改。覆盖安装 APK 时需保持包名与签名；卸载或清除应用数据会删除配置。

APK 构建成功仅证明导出流程完成。真机验收需检查首次启动、创建/加入房间、竞拍大师触摸操作及再次启动后的配置保留。

## 外置文件与目录

正式原样数据固定放在包内 `external/`，不在作者 manifest 中逐项声明。目录不存在表示没有外部数据。工具自动生成 `external_files` / `external_directories` 索引，保留空目录；隐藏文件、链接、导入映射、UID 与备份不作为正式外部文件收录。个人可编辑资料、偏好和存档必须放在此目录外。

游戏使用 `api.get_external_path("external/maps/default.json")` 获取本次启动所选产物的物理路径。FileAccess/DirAccess 可以直接使用；PNG、音频等采用运行时文件加载 API。普通预加载资源留在 PCK 中。正式外部字节参与包 Hash，发布更新会替换并移除旧描述中的退役文件；config/ 不受影响。

普通资源保留 `.import`、`.uid` 和运行时导入产物，已有有效重映射时不重复携带原始媒体；源码 ZIP 保留原始素材和导入参数。打包代码变化自然进入编辑器缓存输入，无独立构建修订计数。包的版本号仍由作者明确维护。

## 可视化 iOS 云导出

编辑器打开“项目 → 工具 → GodotParty：导出 iOS 可玩包”。仍只需勾选内容和选择下载目录。勾选核心生成 `GodotParty-iOS-SideStore.ipa` 与 `GodotParty-content-ios.zip`；不勾选核心只生成内容 ZIP。每次下载存入所选目录中的 `ios-<提交版本>-<运行编号>/`，附带 `build-info.json` 和安装说明，不覆盖其他构建。

Windows 本机需要 Git、GitHub CLI 和 PATH 上的 Godot；先运行 `gh auth login -h github.com`，账户需要该仓库 Actions 的运行权限。后端 `core/dev/export_ios_cloud.ps1` 使用 origin 指向的 GitHub 仓库，只构建已推送的当前 HEAD；未提交修改不会进入云端，尚未推送的提交明确失败。窗口显示提交、工作流链接及构建阶段；详细记录在本次 `tmp/exports/` 目录。修改源码或内容后，应先提交并推送相关小游戏子模块，再推送主仓库引用。

`.github/workflows/build-ios.yml` 在 macOS/Xcode 上检出指定提交及其子模块，安装与本机 Godot 相同版本的编辑器和 iOS 模板。`core/dev/build_ios.py` 复用移动端内容导出流程，自动补齐依赖、重新导入资源，再构建独立的 iOS 框架工程。框架声明 `ios`，使用 Compatibility 渲染、横屏、触摸模拟左键；左上角 Esc 第一次触碰只显现，再点击才发送 Esc。移动端玩法仍须实际适配触摸与设备能力，包版本检查不代替真机验证。

IPA 面向 ARM64 iPad/iPhone，仅带 ad-hoc 签名，必须导入 SideStore 重签安装，不能直接安装，也不是 TestFlight/App Store 包。本流程不接收 Apple 证书。GitHub 保留可玩产物 14 天、构建日志 7 天；构建失败时查看运行链接中的诊断产物。

iOS 配置和内置内容安装到应用私有存储，保留已有玩家配置，正式外置文件按事务更新；更新时保持应用标识和签名身份。卸载或清除应用数据会丢失配置。内容 ZIP 导入后需要重启，不热替换 PCK。云端结构和编译检查不代替 iPad 真机触摸、文件选择器、房间创建及多人联网验收。


## 统一资源收集边界

Windows 与 Android 核心构建共用 `core/dev/export_source_files.ps1`，iOS 使用同一移动暂存工程；核心资源、署名收集均按目录名跳过 `authoring/`，同时继续跳过其他含 `.gdignore` 的子树。普通内容收集使用同样的目录约定，协议不包含其独立 avatars 子包。隐藏文件/目录、临时备份、包内玩家配置不发布；正式 `.import` 与 `.uid` 保留。

内容暂存完整复制作者的导入设置，再由所选 Godot 在干净工程中生成目标资源。声明的外置文件只由外置流程复制一次；构建专用 `.gdignore` 或 Keep File 导入标记阻止它们被再次转换，标记不随外置文件发布。可玩 PCK 的普通导入资源只保留重映射与运行产物；原样文件按其使用方式保留，不按音频/图片扩展名盲目删源文件。

不发布的开发资源统一放入包内 `authoring/`，不使用 `.gdignore` 隐藏开发目录。PowerShell 暂存与 Godot 内容收集均直接排除该目录名（包含嵌套目录），源码 ZIP、PCK 与 Windows / Android / iOS 发布使用相同边界；具体分类和音效/图片单一正式路径规则见 [原版资源开发规范](authoring.md#原版资源开发与发布目录)。

## 资产包

资产包位于 `games/assets/<id>/`，安装到 `assets/<id>/content.pck` 与 `content.pck.json`。目录名是 ID；作者 manifest 仅含 `name`、`kind: "assets"`、`package_version`、`remark`、`framework_version`、`supported_languages` 六个字段，框架版本精确匹配。资产包可包含代码、场景、素材、文档等公共内容，不声明平台、入口、设置或其他内容依赖；包内互相引用，包外仅引用框架公开内容。资产包之间不得相互引用。

协议和游戏用原有 dependencies 声明资产包的版本范围，在编辑器直接引用资产包路径。导出自动补齐依赖，PCK 仅收集所属包的文件与导入产物；下载、来源选择、排队安装和重启规则保持一致。资产包源码 ZIP 文件名必须是 `<id>.zip`，导入时据此恢复目录身份。PCK 描述仍由工具生成，不增加作者维护字段，使用相同包级 Hash。

联机只比较框架版本及所需包的实际版本和 Hash；新增包后需要重新构建并重启。

原版 UI 0.0.1 提供准备/结算展示视图、HUD、资料编辑视图、玩家光标、字体，以及数字动画、轮换大厅、大富翁 UI和未被框架使用的 Ambient Reveal 扩展组件。原版协议保留准备/结算协调及结果校验；资料适配器向 UI 注入协议标识、颜色和颜色名称。框架自身启动、内容管理与下载 UI 不依赖资产包。


## 构建和临时目录

纯依赖选择在 core/content/party_content_selection.gd；隔离导入、PCK 写入和分发缓存生成在 core/dev/party_shared_pack_builder.gd。发布核心不包含或预加载 core/dev。编辑器启动阶段加载构建器；运行期间只分发已冻结的产物。批量选定集合只暂存、导入一次，再按每包归属写独立 PCK；启动构建复用同一实现。隔离 PCK 构建工程串行导入资源，避开本次全量验证中重复崩溃的并行字体导入路径。头像包随所属协议一起判定可用性；协议不可用时，其头像也不挂载或注册脚本类型。

内容请求、准备、数据块、完成及取消使用 CONTENT_CHANNEL=8，可靠性由 ENet 提供。每客户端一次下载一个文件，32 KiB/块、8 块在途；房主每客户端队列最多 16 项，每帧轮流处理最多 16 块。任务 ID 隔离重试与取消，接收校验文件及偏移。复用文件句柄，约 1 MiB 或文件结束刷新。ZIP 写入和入队复制按约 1 MiB 分帧，显示下载、整理文件、等待重启状态。

构建成功并验证产物后删除本次 tmp/content_build 工作目录；失败保留日志，删除可再生源码及导入副本。下载成功入队、失败或明确取消时关闭句柄并回收本任务 tmp/content_download；完整待安装 tmp/content_update.zip 保留至启动安装成功，入队失败不改动此前任务。tmp/content_distribution 保留当前有效版本。不要在任一实例运行时清理其他实例的遗留目录；离线清理入口为 core/dev/clear_content_work.ps1，保留 tmp/local 与所有包 config。根 assets/ 只存安装内容并由 Git/Godot 忽略；games/assets/ 是版本控制中的开发源码。
