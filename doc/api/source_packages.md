# 源码与 PCK 内容包

## 入房内容同步

内容检查分两段：加入时检查当前房间的协议、主游戏及其必需依赖/形象包；房主点击开始时检查所选小游戏池和完整依赖。无关的已安装游戏不要求客机同步。缺失或版本不一致时显示列表、当前/目标版本及每项“下载/更新”按钮，底部为“全部同步”和“返回”。框架不匹配仍须手动更新。所有下载共用当前 ENet UDP 连接，不另开 HTTP/TCP 端口。

房主点击开始后，所有玩家检查通过、在线且准备完成便直接开始，不弹窗。只有缺包、版本问题或断开等需要等待时，房主才显示“等待客机下载”，逐人显示检查、准备分发包、下载进度、等待重启或复查状态，底部仅有“终止并返回房间”。全部重新通过检查并就绪后自动开始。终止会取消本轮检查并关闭客机下载页，已入房的客机留在房间；客机自己返回则离开房间。等待期间改变房间配置或依赖会取消本轮检查，需要重新开始。下载后断开并重新加入仍使用同一玩家身份复查。

协议和游戏的 supported_systems 参与两段兼容检查，形象包继承所属协议声明；平台不支持的条目显示红字“平台不支持”，禁用单项和全部同步按钮。editor 为独立系统标识，暂时也接受 windows 声明；android 需要显式支持。内容齐全但平台不支持也会拦截，下载不会改变平台兼容性。

发布版房主直接提供安装目录中的 content.pck、content.pck.json 和声明的外置资源。编辑器源码房主无需手动导出：客机点击单项下载/更新或“全部同步”后，房主按需在隔离工程中导入并生成共享 PCK，随后传输。隔离导入同时开启桌面 S3TC/BPTC 与移动 ETC2/ASTC 资源；相同内容 PCK 可以用于 Windows、Android，实际玩法支持仍由声明决定。后台构建期间继续处理网络消息，同一房主串行构建并复用缓存。准备期间显示“正在准备分发包”；导入或导出失败会在客机显示错误和日志路径，可重试。不会覆盖客机编辑器工程中的源码包。

编辑器分发缓存位于安装根目录 tmp/content_distribution/，按包类别/ID、package_version、框架版本、引擎版本和公共打包构建修订号隔离。完整导出并检查后才发布缓存索引；后续客机及后续运行复用同版本缓存。缺失或不完整的缓存生成新副本，旧副本不作为成功结果发送。无文件哈希检查；修改源码后必须更新 package_version，未升版本的源码修改不会自动使缓存失效。

逐项操作下载到 tmp/content_download/，每包显示累计已下载/总大小（MB，1 MB = 1,000,000 字节）、主题 ProgressBar 和 MB/s；速率按约半秒采样，停流后归零，重试时该包进度重新计数。分发包准备完成前总大小显示“待获取”。全部差异项完成并成功排队安装后，弹窗提示“更新后需要重启”，只提供“退出游戏”按钮，点击直接退出。用户下次启动时安装，再手动加入房间；不自动重启、不保存或读取重连目标。房主显示等待客机重启后手动加入，重新加入后复查，通过后才允许开始。保留 config/、存档及已存在的外置可编辑文件，外置文件按现有安装契约仅补齐缺失项。返回会断开连接并取消当前传输；已经完整排队的安装包保留到下次启动。

房主断开时，客机清理连接、房间与活动场景，弹窗显示“房主已退出”，确认后留在主菜单，不保留离线大厅。

下载超时或写入失败会显示错误并可重试；重试从该包开头下载，不支持跨连接断点续传。当前为首次实现，尚未实现只激活房间依赖集合、外置可编辑文件的强制版本替换或跨版本协议配置迁移。

启动时只枚举各分类的直接子目录并读取 manifest，按 ID 登记及分配网络通道。协议、主游戏与小游戏须声明 localization；显示文本时按需读取包内 PO，访问设置时才加载设置脚本。发布源码 ZIP 或 PCK 时检查该包的完整声明、设置与翻译。见 [本地化](localization.md)。

完整开发工程保留 core/、games/、doc/、addons/；测试专用内容只放在 tmp/test/，不属于发布包。源码包位于 games/{protocols,maingame,minigame}/<id>/；形象包位于 games/protocols/<protocol_id>/avatars/<id>/，其清单声明 owner_protocol。manifest.json 是唯一作者维护的内容目录项，包 ID 全局唯一。

玩家安装目录见 [配置与预设](configuration.md)。协议、maingame、minigame 分别放入对应根文件夹，每包单独目录，包含 content.pck 和 content.pck.json；形象包放入所属协议 avatars/。替换版本时只替换这两个生成文件，保留 config/。安装、删除、更新及来源切换后重新启动，不做热替换。

编辑器“项目 → 工具”提供“GodotParty：导出 Windows 可玩包”、“GodotParty：导出 Android 可玩包”和“GodotParty：导出 iOS 可玩包”三个入口。窗口内勾选内容并选择输出目录；不勾选核心即可仅导出独立内容更新。导出前完成资源导入，导出器跳过含 .gdignore 的目录及其整个子树，不收集其中的旧原型、资源和导入映射。批量导出脚本 core/dev/export_content.gd 自动生成标准目录和 content.pck 文件名。

描述格式 4 包含构建信息、包 ID/版本/类别、supported_systems、文件路径索引、UID 索引和 script_classes 类型清单，形象包另含 owner_protocol；不含文件哈希。内容 ZIP 使用 bundle 格式 2，不再带 platform 字段，不按请求者系统生成不同内容副本。框架检查目录归属、声明路径、UID 和类型名冲突、核心/引擎版本、挂载后清单及依赖版本。协议 PCK 不重复包含 avatars 子包。房间比较包版本与配置快照；相同版本号不证明文件字节相同，作者修改内容或支持系统后必须更新 package_version。

若同 ID 同时有源码和 PCK，必须在内容包来源中明确选择，或使用 --party-source=<id>:source/pck 后重启。--party-pack-dir=<安装根目录> 支持隔离验收，里面仍使用三个分类目录。源码与 PCK 保持相同 res://games 虚拟路径；用户局部配置不放入 PCK。

dependencies 是包 ID 到精确 package_version 的映射。升级协议时，须检查全部已安装主游戏、小游戏及适配器的依赖；确认调用契约后同步依赖值，并递增修改过的内容包自身版本，再成套导出。不要只改导出描述文件的版本号，因为实际清单在 PCK 内。小游戏 adapters 的依赖只在选中接入时激活。公开资源通过 package_id/resource_key 引用。不要预加载未选协议或依赖另一份 core；普通内容只引用公开 core/api、core/ui 契约。内容使用普通 Godot 脚本能力，加载检查不是安全沙箱。

独立内容包支持直接使用 `class_name` 注册的类型，例如 `var audio: PartyGameAudio`。导出器从已导入的类型信息中只提取本包实际打包的脚本，生成 script_classes；作者不维护第二份注册表。共享组件、资源和核心数据类型才注册全局名称，名称必须在整个安装中唯一。跨包引用须声明相应依赖，不要引用未安装的可选协议。

启动时先校验全部描述和类型继承关系，再挂载普通 PCK、校验清单与依赖，最后合并核心及所选内容的类型注册信息，完成注册后才加载内容脚本。普通 PCK 仍不覆盖框架资源；只有框架生成的注册表 ZIP 覆盖 `.godot/global_script_class_cache.cfg`。这不需要把整个开发工程的缓存塞入核心。生成文件位于安装目录 `tmp/content_classes/<进程ID>.zip`，每次启动重建，全部实例退出后可以删除该缓存目录。

从旧描述格式升级时，须重新导出核心及所有已安装内容包；旧格式会明确拒绝加载。manifest 格式仍为 2。完成这次升级后，普通小游戏更新仍可单独导出并替换其 content.pck 和 content.pck.json；若改变依赖版本，须一起更新对应依赖。退出游戏后更新并重新启动，保留 config/。新增或修改全局类型后，发布验收应覆盖实际导出的 EXE 创建房间和受影响小游戏入口，不能只依赖编辑器运行。

## 可视化 Windows 导出

编辑器打开“项目 → 工具 → GodotParty：导出 Windows 可玩包”。界面只需勾选核心、协议及形象包、主游戏、小游戏，再选择输出目录。点击开始导出后显示进度、错误和构建日志目录。

勾选内容会自动补齐精确版本依赖、所属协议以及小游戏适配器的协议和依赖；自动勾选项标注“依赖”。导出会包含所选小游戏的全部已声明适配器依赖。主游戏的小游戏池由房主在运行时选择，导出主游戏不会自动打包所有候选小游戏。仅勾选内容可生成独立更新包，勾选核心时同时构建 Windows x64 EXE。

原版协议包含两个独立形象包。godot_party_default_avatars_2d 提供六个 2D 头像，godot_party_default_avatars 提供 Cube 3D 占位。包均位于 protocols/<协议ID>/avatars/<包ID>/，默认依赖会一起勾选。旧玩家资料中的协议内头像引用需在个人资料界面重新选择并应用。

选择项目外目录，或本项目 tmp/releases/ 下的目录（验收产物可放 tmp/test/）。后台使用 PATH 上的 godot 和匹配的 Windows 模板，在 tmp/exports/ 下构建核心副本、日志和中间产物。核心副本排除内容、开发插件、个人 JSON 配置和存档，并关闭场景文本到二进制转换以保留嵌套 UI。不会启动项目升级。

全部构建成功后才写入输出目录。已有 EXE、content.pck 和 content.pck.json 成套更新；已有配置、用户新增文件与外置资源文件保留，缺少的外置资源补齐。分发更新的外置默认数据时，作者应使用新路径或指导用户显式替换。发布失败会回滚已覆盖文件，备份保留在构建目录。导出期间请关闭目标目录中的游戏；同一目标目录同时只允许一次导出。

完整安装目录可直接通过 Windows 文件资源管理器合并。形象包保留所属协议路径。首次分发时不要附带测试启动生成的 core/config/settings.json，避免复制 player_id。应用偏好后生成的 JSON 位于各包 config/ 下，退出游戏后可以手动编辑。

core/dev/export_release.ps1 是窗口使用的同一后端，接收 RequestPath 指向的 JSON。请求包含 core 布尔值、output 绝对目录和 packages 包 ID 数组。export_windows_host.ps1 可单独构建核心；export_windows_minimal.ps1 是原版轮换与阿瓦隆的预设，复用同一后端和依赖计算。运行后仍需检查正式菜单、设置和实际开局；导出成功不等于多人或外网验收。

## 可视化 Android 导出

通常使用 Godot 编辑器设置中的 SDK 路径。若运行中的编辑器反复写回旧 SDK 配置，可在本机 `tmp/local/android_export.json` 写入 `{"android_sdk_path":"F:/AndroidSDK"}`。可视化导出器会提前检查该目录，并在隔离的 APK 导出进程内应用此路径；该文件不提交、不进入可玩包，也不增加导出窗口选项。没有此文件时仍使用编辑器设置，存在但无效时明确失败，不自动猜测 SDK 位置。

编辑器打开“项目 → 工具 → GodotParty：导出 Android 可玩包”。仍只需勾选内容和选择输出目录，依赖选择规则与 Windows 相同。勾选核心会生成 `GodotParty.apk`，同时生成 `GodotParty-content-android.zip`；不勾选核心则只生成内容 ZIP，用于单独更新小游戏。后端请求增加 `platform: "Android"`，省略时仍导出 Windows。

当前 APK 是 ARM64、横屏、调试签名的测试包，使用本机 Godot 已配置的 Android SDK、Java 和匹配导出模板。导出器在隔离工程中导入 Android 资源，使用 Compatibility 渲染器，并启用屏幕触摸模拟鼠标左键；不会把触摸变成键盘操作，也不提供虚拟摇杆。需要键盘或鼠标右键的小游戏仍须另行适配。初版选择小游戏轮换与竞拍大师。

APK 内置所选共享内容 ZIP；首次启动在应用私有存储中安装各包，再挂载 PCK 和注册 `class_name`。每个新 APK 构建首次运行会更新内置内容，已有 config/ 和已存在的外置数据文件保留，缺少的默认外置文件补齐。内容安装前校验描述和路径，平台是否可游玩由入房/开始检查决定。独立 ZIP 也使用相同目录与校验，不将配置打包。Android 导出同样生成包含两种纹理导入格式的 PCK，可直接分发给 Windows 客机；框架 EXE/APK 仍分别构建。

Android 不使用 Windows 文件资源管理器直接合并安装目录。在“内容包”中选择 Android 内容 ZIP，完全退出应用再打开后生效，不热替换正在使用的 PCK。原生文件选择器要求 Android 10 或更新系统；系统配置 JSON 可在此导出、编辑并导入，玩家身份保留。游戏偏好仍通过游戏内设置修改。覆盖安装 APK 时需保持包名与签名；卸载或清除应用数据会删除配置。

APK 构建成功仅证明导出流程完成。真机验收需检查首次启动、创建/加入房间、竞拍大师触摸操作及再次启动后的配置保留。

## 外置文件与目录

内容作者在 manifest.json 的 external_files 数组声明包内相对路径，目录必须以 / 结尾，文件不带结尾 /。例如 "external_files": ["charts/", "maps/default.json"]。省略时表示没有外置数据。路径大小写应与磁盘一致，不支持通配符、上级路径、链接、重叠声明及 config/、avatars/、manifest.json、content.pck、content.pck.json 等保留位置。

声明的文件和目录必须存在，空目录保留。导出器把它们原样复制到包安装目录，保留层级，并从 PCK 排除相应文件、UID 与导入映射。包内 config/、隐藏目录、备份和临时文件不发布。工具生成的描述文件记录 external_files 和 external_directories；启动和安装时检查这些数据是否齐全。使用内置安装器安装外置资源包时，PCK、描述文件和外置内容必须按原相对位置放在一起。

游戏通过 api.get_external_path("charts") 或 api.get_external_path("maps/default.json") 获取本包声明范围内的绝对路径。编辑器运行返回源码包下的位置，导出运行返回安装目录；--party-pack-dir 验收目录也被支持。此接口不创建文件，未声明路径明确报错。FileAccess、DirAccess 可直接使用返回路径；原始 PNG、OGG 等应使用支持运行时文件的加载 API。预加载资源仍须放在 PCK 中，不能将预加载所依赖的文件改成外置。

所有内容包统一通过公共打包器生成。已有有效导入映射的资源仅收录 `.import` 和对应运行时产物，不重复收录原始素材；保留共享包所需的桌面与移动纹理变体。UID 可以指向由包内 `.import` 映射的原始虚拟路径。没有运行时重映射的文件保持原样；直接读取原始素材的功能应使用 `external_files`。源码 ZIP 保留原始素材供重新导入。公共打包规则变化时递增构建修订号，使编辑器分发不再复用旧构建。

普通场景、贴图和脚本按包内相对结构装入 PCK。外置声明用于确实需要用户编辑、扩展或通过文件系统读取的数据。作者负责文件格式校验，文件内容不参与联机一致性比较。


## 可视化 iOS 云导出

编辑器打开“项目 → 工具 → GodotParty：导出 iOS 可玩包”。仍只需勾选内容和选择下载目录。勾选核心生成 `GodotParty-iOS-SideStore.ipa` 与 `GodotParty-content-ios.zip`；不勾选核心只生成内容 ZIP。每次下载存入所选目录中的 `ios-<提交版本>-<运行编号>/`，附带 `build-info.json` 和安装说明，不覆盖其他构建。

Windows 本机需要 Git、GitHub CLI 和 PATH 上的 Godot；先运行 `gh auth login -h github.com`，账户需要该仓库 Actions 的运行权限。后端 `core/dev/export_ios_cloud.ps1` 使用 origin 指向的 GitHub 仓库，只构建已推送的当前 HEAD；未提交修改不会进入云端，尚未推送的提交明确失败。窗口显示提交、工作流链接及构建阶段；详细记录在本次 `tmp/exports/` 目录。修改源码或内容后，应先提交并推送相关小游戏子模块，再推送主仓库引用。

`.github/workflows/build-ios.yml` 在 macOS/Xcode 上检出指定提交及其子模块，安装与本机 Godot 相同版本的编辑器和 iOS 模板。`core/dev/build_ios.py` 复用移动端内容导出流程，自动补齐依赖、重新导入资源，再构建独立的 iOS 框架工程。框架声明 `ios`，使用 Compatibility 渲染、横屏、触摸模拟左键；左上角 Esc 第一次触碰只显现，再点击才发送 Esc。初版 iOS 玩法声明覆盖原版协议、小游戏轮换和竞拍大师，其他小游戏需要各自适配后声明。

IPA 面向 ARM64 iPad/iPhone，仅带 ad-hoc 签名，必须导入 SideStore 重签安装，不能直接安装，也不是 TestFlight/App Store 包。本流程不接收 Apple 证书。GitHub 保留可玩产物 14 天、构建日志 7 天；构建失败时查看运行链接中的诊断产物。

iOS 配置和内置内容安装到应用私有存储，保留已有玩家配置及外置文件；更新时保持应用标识和签名身份。卸载或清除应用数据会丢失配置。内容 ZIP 导入后需要重启，不热替换 PCK。云端结构和编译检查不代替 iPad 真机触摸、文件选择器、房间创建及多人联网验收。


## 统一资源收集边界

Windows 与 Android 核心构建共用 `core/dev/export_source_files.ps1`，iOS 使用同一移动暂存工程；核心资源、署名收集均跳过含 `.gdignore` 的整个子树。普通内容收集使用同样的目录约定，协议不包含其独立 avatars 子包。隐藏文件/目录、临时备份、包内玩家配置不发布；正式 `.import` 与 `.uid` 保留。

内容暂存完整复制作者的导入设置，再由所选 Godot 在干净工程中生成目标资源。声明的外置文件只由外置流程复制一次；构建专用 `.gdignore` 或 Keep File 导入标记阻止它们被再次转换，标记不随外置文件发布。可玩 PCK 的普通导入资源只保留重映射与运行产物；原样文件按其使用方式保留，不按音频/图片扩展名盲目删源文件。

不发布的开发资源统一采用包内 `authoring/.gdignore`；具体分类和音效/图片单一正式路径规则见 [原版资源开发规范](authoring.md#原版资源开发与发布目录)。

## 资产包

资产包位于 `games/assets/<id>/`，安装到 `assets/<id>/content.pck` 与 `content.pck.json`。目录名是 ID；作者 manifest 仅含 `name`、`kind: "assets"`、`package_version`、`remark`、`framework_version` 五个字段，框架版本精确匹配。资产包可包含代码、场景、素材、文档等公共内容，不声明平台、入口、设置或其他内容依赖；包内互相引用，包外仅引用框架公开内容。资产包之间不得相互引用。

协议和游戏用原有 dependencies 声明资产包的精确版本，在编辑器直接引用资产包路径。导出自动补齐依赖，PCK 仅收集所属包的文件与导入产物；下载、来源选择、排队安装和重启规则保持一致。资产包源码 ZIP 文件名必须是 `<id>.zip`，导入时据此恢复目录身份。PCK 描述仍由工具生成，不增加作者维护字段，也不计算文件哈希。

网络协议为 18：同步清单携带包类型，资产包不参与平台限制；使用它的协议和游戏仍声明各自支持平台。新增资产类型后请成套重新导出框架和受影响内容。

原版 UI 1.0.2 提供准备/结算展示视图、HUD、资料编辑视图、玩家光标、字体，以及数字动画、轮换大厅、大富翁 UI、旧设置页和未被框架使用的 Ambient Reveal 扩展组件。原版协议保留准备/结算协调及结果校验；资料适配器向 UI 注入协议标识、颜色和颜色名称。框架自身启动、内容管理与下载 UI 不依赖资产包。
