# 可开局人数

协议、大游戏、小游戏的入口脚本 `static func party_definition() -> Dictionary` 返回 `player_counts`：1–8 之间不重复的整数数组。连续区间也逐一列出；数组顺序不影响结果。头像包不需要声明。人数规则不进入内容 manifest。

```gdscript
static func party_definition() -> Dictionary:
    return {
        "player_counts": [1, 2, 3, 4, 5, 6, 7, 8],
        "player_count_rules": [
            {"when": {"mode": "team"}, "counts": [2, 4, 6, 8]}
        ]
    }
```

`player_count_rules` 可省略。`when` 引用本包配置 Schema 中的 room 字段，所有键值同时相等时生效；字段默认值也参与判断。字段、枚举值及类型必须有效，不能引用 local 偏好。上例要求 Schema 声明 `mode`，其枚举包括 `team`。规则只收窄静态人数集合，多个命中的规则继续取交集，不采用第一条或最后一条覆盖。声明的 counts 不能为空，但计算得到的交集可以为空。

大厅允许人数 = 大游戏的有效人数 ∩ 每个已选小游戏的有效人数。每个游戏的有效人数 = 本游戏静态及配置限制 ∩ 所绑定协议的静态及配置限制。协议条件使用该游戏生效的公共房间规则（默认值、房间基值、该游戏覆盖），游戏条件使用自身房间规则；不会继承大游戏的专属设置或本地偏好。

例如：协议 1–8 人，大游戏 `[1,3,6]`，已选小游戏团队赛 `[2,4,6,8]`，最终只允许 **6 人**。选择多个小游戏、多个池时，所有已选项都参与交集；重复项不改变结果。未选中的配置草稿、已安装但未选中的小游戏不参与计算。

修改房间配置、公共规则覆盖、小游戏池或预设后重新计算。空交集允许保留草稿以便继续调整，但房间不能开始。大厅向房主和客户端显示当前人数不符原因；小游戏池显示草稿允许的开局人数和当前小游戏在配置下的参赛人数。人数满足后仍须满足玩家准备、内容确认及恢复会话的原有条件。房间容量仍为八人，人数限制控制能否开始，不阻止大厅凑人。

大游戏的限制用于大厅总人数。启动前景小游戏时，实际参赛子集另外满足该小游戏及协议的有效人数，其他人仍可观战。例如六人大厅的小游戏允许 2、4、6 人时，可以启动两人子局。检查使用本轮即将锁定的房间规则；运行中 next_round 修改只影响后续子局，不改变已经开始的一轮。

框架内部共享计算位于 `core/config/party_player_counts.gd`。`party_connection.allowed_player_counts()` 返回当前大厅集合；`start_reason()` 在房主开始前强制检查；协调器在子局请求时再次检查实际参赛人数。客户端根据房主发布的房间快照计算展示，不单独同步另一份可修改的人数限制。

原人数回归脚本已退役归档。后续人数规则变更按需要在 `tmp/test/` 定向验证集合交集、开始门槛和参赛子集；联机行为仍需独立的编辑器多人验收。
