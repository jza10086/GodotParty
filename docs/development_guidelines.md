# GodotParty 开发规范

本文档记录 GodotParty 当前的开发原则和默认技术决策。项目按独立游戏规模开发：优先完成可玩的整体框架和功能闭环，之后再依据真实问题优化。

根目录 `AGENTS.md` 是供 Codex 执行的简明硬规则；本文档负责解释原因、边界和建议实现方式。两者冲突时，应澄清并同步修改，不能长期保留两套规则。

## 1. 项目目标和非目标

GodotParty 是一个最多八人的在线派对游戏，四人体验是早期开发、调试和平衡的重点。

当前不做：

- 同屏本地多人和电脑 AI 玩家。
- 专用服务器、房主迁移和断线重连。
- 严格反作弊体系。
- 为未来假设设计的企业级架构。
- 在整体框架完成前进行大规模性能优化。

## 2. 游戏模式层级

主要模式由“大游戏 + 中游戏 + 小游戏”组成。

### 2.1 大游戏

大游戏是全局流程基底，例如大富翁式棋盘。它负责长期进度、回合推进、玩家总体资源和中小型游戏的选择或触发。

### 2.2 中游戏

中游戏通过 tag 与小游戏区分。中游戏通常持续时间更长，可以包含跨回合属性，例如拍卖游戏的剩余金钱，并可向大游戏提供更高或更多类型的胜者奖励。

跨回合状态必须由明确的数据对象保存，并在进入、离开及重新开始中游戏时定义生命周期，不能依赖场景节点碰巧没有释放。

### 2.3 小游戏

小游戏通常时间较短、规则独立、结算直接。每个小游戏拥有自己的状态机和网络同步策略。

### 2.4 次要模式和首个垂直切片

次要模式连续运行中游戏和小游戏，不经过大游戏棋盘。首先用该模式验证框架：

1. 创建房间。
2. 客户端加入大厅。
3. 玩家准备。
4. 房主开始。
5. 所有客户端加载占位小游戏。
6. 房主确认客户端就绪并统一开始。
7. 小游戏结束并同步排名。
8. 返回大厅或进入下一游戏。

在该流程稳定前，不扩展大量正式小游戏或完整大游戏内容。

## 3. 语言与类型

项目默认只使用 GDScript。只有分析器确认存在严重瓶颈，且算法、数据结构、调用频率和普通 GDScript 优化均不足时，才考虑迁移清晰的热点。

小型热点优先考虑 GDExtension。只有整个子系统因类型系统、生态库或计算规模明显受益时才考虑 C#。不能仅凭“理论上更快”提前混用语言。

禁止使用 `:=`。成员变量、局部变量、参数和返回值都应显式声明类型：

    var move_speed: float = 300.0
    var current_score: int = 0
    var players: Array[PlayerData] = []

    @export var score_label: Label
    @export var rules: MinigameRules

    func get_player(peer_id: int) -> PlayerData:
        return players_by_peer.get(peer_id) as PlayerData

确实需要多种输入类型时显式写 `Variant`。动态类型必须是有意设计，不能来自遗漏。

## 4. 命名规范

- 场景、脚本和资源文件：`snake_case`。
- 变量、函数和信号：`snake_case`。
- 信号按事件语义命名，例如 `player_joined`、`score_changed`。
- 常量和枚举成员：`UPPER_SNAKE_CASE`。
- 节点名称、枚举类型和 `class_name`：`PascalCase`。
- 脚本通常与主场景同名，例如 `multiplayer_lobby.tscn` 和 `multiplayer_lobby.gd`。

只为跨模块共享的组件、自定义 Resource、核心数据类型以及需要从编辑器创建的对象声明 `class_name`。普通场景附属脚本不占用全局类名。

## 5. 目录组织

优先按功能聚合，而不是把全部脚本和场景机械分离：

    game/
      core/
      session/
      lobby/
      large_game/
      games/
        medium/
        minigames/
    ui/
    shared/
    autoload/
    resources/
    assets/
    addons/
    tools/dev/
    docs/

每个小游戏目录可包含自己的场景、脚本、状态、资源和配置定义。只有确实被多个游戏共用的内容才移动到 `shared/`。

## 6. 场景和依赖

优先使用场景组合与职责明确的小组件，避免深层继承。

- 跨场景依赖、可替换节点和设计参数使用 `@export`。
- 同一场景内部、结构稳定且不需要替换的私有节点允许使用 `%UniqueNode`。
- `$NodePath` 仅用于非常简单、稳定的私有节点路径。
- 必需引用应在 `_ready()` 或专门验证函数中检查。
- 缺少必需依赖时使用断言或明确错误，不允许静默跳过。

静态规则与模板使用自定义 `Resource`。实时血量、分数、局内状态等放在运行时节点或数据对象中。若需要修改从磁盘加载的共享 Resource，应先复制，避免多个实例共同修改模板。

## 7. Autoload 边界

只有生命周期确实跨场景的全局服务才使用 Autoload。

- `NetworkManager`：Peer 生命周期、连接状态、连接事件，以及 ENet、直连和 Steam 传输层的替换边界。它不负责具体小游戏规则、角色节点和 UI。
- `GameSession`：本地玩家标识与 Peer ID 的关联、玩家名单、显示名、当前模式、大游戏总体状态和跨场景数据。离开房间时必须调用明确的 `reset_session()`。
- `SignalBus`：只传递跨场景通用事件，不保存状态，也不替代局部信号。

`SceneRouter`、`AudioManager` 和 `SaveManager` 在确有需要时再加入，不要求项目开始时一次性创建所有单例。

## 8. 中小游戏统一接口

共享 `MinigameController` 只规定外部生命周期，不规定游戏内部实现：

    prepare
    countdown
    start
    finish
    show_results
    cleanup

接口至少应能表达游戏 ID、类型 tag、规则资源、玩家数量、随机种子、客户端加载状态、排名结果、上层奖励以及本游戏的网络同步策略。

每个中游戏和小游戏设计独立状态机。简单状态机使用本游戏自己的枚举、当前状态变量和集中式切换函数；复杂后再拆成状态节点。不要提前建立重量级通用状态机框架。

小游戏不能直接决定大厅、大游戏或全局场景如何跳转，只能向上层返回结果和结束原因。

## 9. 网络架构

### 9.1 开发顺序

1. 使用 Godot 高级多人 API 和 `ENetMultiplayerPeer` 完成本机多客户端框架。
2. 框架稳定后支持 IPv4、IPv6 地址直连。
3. 再接入 Steam 大厅、好友邀请、中继或 Steam 网络传输。

玩法层不能直接创建 ENet Peer，也不能假定传输一定来自 ENet。连接流程集中在 `NetworkManager` 中。

### 9.2 房主权威与玩法策略

会话层采用房主权威，但不要求所有小游戏使用完全相同的实时同步方式。

- 回合制卡牌等玩法可以由房主完整计算，客户端只提交操作请求。
- 普通动作玩法可由房主维护权威状态，同时客户端进行输入预测或表现层反馈。
- 音游等强调即时反馈的玩法允许客户端本地判定并上报结果。
- 初期不做严格反作弊，但房主仍应验证消息类型、发送者、数值范围和当前状态，防止错误消息破坏会话。

小游戏通过接口声明同步策略；框架提供连接、消息路由、玩家映射、加载同步、时间基准和结果提交等能力。物理按键不能通过网络发送，客户端应先把输入转换为逻辑动作或受约束的玩法请求。

### 9.3 同步加载

房主选择游戏 ID、规则和随机种子并广播加载命令。客户端完成场景初始化后报告 ready。房主等待全部必需客户端或触发明确的超时策略，再广播统一开始时间。客户端不能因为本机加载较快而自行开始。

### 9.4 断线规则

- 大厅中断线：移除玩家并更新列表。
- 游戏中断线：该玩家记为退出或最后一名，具体结果由玩法决定。
- 房主断线：结束会话，其他玩家返回主菜单。
- 暂不支持重连和房主迁移。

## 10. 输入系统

游戏启动时加载全局 InputMap。所有代码读取逻辑动作，不直接判断具体键值。

通用动作包括 `move_up`、`move_down`、`move_left`、`move_right`、`interact` 和 `pause`。小游戏特有动作使用清晰前缀，例如 `shooter_fire`、`shooter_reload`、`rhythm_hit`。

查询动作时，当前小游戏的映射优先；若小游戏配置没有定义对应动作，则回退到全局配置。这样同一个鼠标左键可以在射击游戏中代表开火，在音游中代表击打，同时仍能复用全局 WASD 移动。

第一阶段只正式支持键盘和鼠标。输入读取逻辑应隔离物理设备细节，以便以后添加手柄，但暂不制作手柄映射和交互。网络中只传输逻辑动作或游戏请求，每个客户端只保存自己的按键设置。

## 11. 配置文件

通用设置使用 `ConfigFile` 保存到 `user://settings.cfg`，包括全局按键、音量、显示模式、UI 缩放和配置版本号。

每个小游戏有独立配置文件。第一次进入时若不存在则由默认配置生成；存在则直接加载，并处理版本升级和无效值。建议路径：

    user://minigames/<game_id>.cfg

小游戏配置必须使用稳定 `game_id`，不能依赖显示名称或场景文件名作为永久身份。配置仅保存在本机，不通过 Git 或网络同步。

## 12. UI 与分辨率

基础设计分辨率为 1920x1080；2560x1440 和 3840x2160 是推荐验证分辨率。三者均为 16:9，因此应保持几乎完全一致的构图。

项目采用：

    window/size/viewport_width = 1920
    window/size/viewport_height = 1080
    window/stretch/mode = canvas_items
    window/stretch/aspect = expand
    stretch scale mode = fractional

`canvas_items` 使 UI 按基础尺寸布局，同时在目标分辨率直接渲染。`expand` 保持比例，在非 16:9 屏幕上显示更多水平或垂直区域，不会拉宽控件。

- UI 场景使用全屏 `Control` 根节点。
- 优先使用 `MarginContainer`、`VBoxContainer`、`HBoxContainer` 和 `GridContainer`。
- HUD 锚定到对应角落，中央菜单锚定中心。
- 主要布局不依赖绝对屏幕坐标。
- 面板使用 `StyleBox` 或九宫格纹理。
- 图标优先使用 SVG 或足够高分辨率的纹理，字体使用动态字体。
- 超宽屏可以显示更多场景区域，但关键 UI 应留在合理安全区域内。
- 后续将 UI 缩放作为独立可访问性设置，不与渲染分辨率绑定。

## 13. 错误、日志与注释

程序员错误和不可能状态使用 `assert`。可恢复问题使用 `push_warning()` 或 `push_error()`，并执行明确的恢复或退出路径。不允许无声失败。

网络连接、玩家加入离开、场景加载、游戏开始结束和关键结算保留简洁日志。暂不建设复杂日志框架。

模块开头在职责不明显时说明作用和边界。公共函数和复杂私有函数使用 `##` 文档注释，重点解释作用、重要输入、返回结果、副作用以及容易误用的前置条件。简单 getter、setter、生命周期回调或完全自解释的函数不写重复注释。

## 14. 测试与验收

不追求逐函数单元测试和覆盖率。一个完整模块或可玩闭环完成后再集中测试。

人工验收使用 Godot 编辑器的多实例运行能力，早期重点是一个房主加三个客户端，必要时扩展到八个实例。

纯数值逻辑、配置升级、序列化、网络消息约束和严重 Bug 回归适合自动测试。UI、操作手感、物理、动画、音游时机和多客户端完整流程必须保留人工验收。

AI 可以自行创建轻量调试入口、启动脚本或测试替身来提高重复验证效率，但必须把自动结果与编辑器人工验收、真实 IPv4/IPv6 环境和 Steam 验证分开报告。

## 15. 插件与第三方依赖

- 只有明显节省实现和维护成本时才引入插件。
- 引入前检查 Godot 4.7 兼容性、维护状态和许可证。
- 插件放在 `addons/`，并记录来源、版本和许可证。
- 小功能不引入大型框架。
- 核心逻辑通过简单适配层使用插件，避免业务代码遍布插件 API。

## 16. Git 工作流

项目全部在 `main` 开发，不创建功能分支，除非以后明确修改规则。

- `main` 应保持能够启动。
- 完成一个连贯、可描述的功能后提交，不要求每个小改动都提交。
- 提交信息使用简洁英文祈使句，例如 `Add minigame loading handshake`。
- 不提交 `user://` 设置、导入缓存、凭据和导出凭据。
- 模块完成时分别记录自动检查、编辑器人工验收、真实网络验证和 Steam 验证状态。
